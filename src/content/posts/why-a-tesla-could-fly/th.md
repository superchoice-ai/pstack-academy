Tesla ไม่ได้บิน บทความนี้ไม่ได้อ้างว่ารถคันหนึ่งจะบิน และไม่ได้อ้างว่าใครที่ Tesla ขอให้มันบิน ชื่อเรื่องเป็นอุปมา ภาพคือเครื่องจักรหนักที่เก่งเรื่องอยู่บนถนน แล้วคำถามอีกข้อคือ อะไรเกิดขึ้นกับผลิตภัณฑ์ที่ซับซ้อน เมื่อคนที่แก้มันพิสูจน์การเปลี่ยนแปลงแต่ละครั้งกับของที่รันอยู่ได้ แทนการเถียงจากผลคอมไพล์กับความรู้สึก

คำว่าบินในภาพนี้ไม่ใช่อากาศพลศาสตร์ มันคือแรงยกที่มาจากเครื่องวัด ทีมที่ปิดลูปของตัวเองได้จะลองงานที่เคยต้องนั่งเฝ้า นั่นคือ "การบิน" เดียวที่บทความนี้ยอมพูดถึง

## เธอไม่ได้ทำงานที่ Tesla

Lauren Tan ไม่ได้ทำงานที่ Tesla ไม่มีบันทึกสาธารณะที่สถาบันนี้อ้างอิงบอกว่าเธอทำ เราไม่ได้กำลังเล่าโครงการของ Tesla ตำแหน่งที่ Tesla หรือการรับรองใด ๆ ถ้าจะจำประโยคเดียวจากบทความนี้ ให้จำประโยคนั้น รถเป็นอุปมาของเครื่องจักรที่ยาก ส่วนวิศวกรเป็นคนจริงที่งานสาธารณะอยู่ที่อื่น

โปรไฟล์ GitHub ของเธอที่ [github.com/poteto](https://github.com/poteto) บรรยายว่าเธอเป็นซอฟต์แวร์เอนจิเนียร์ที่ xAI และอยู่ในทีมแกน React Compiler [README ของ pstack](https://github.com/cursor/plugins/blob/main/pstack/README.md) ในรีโพซิทอรีปลั๊กอินของ Cursor บอกว่าเธอทำงานกับโค้ดหลายล้านบรรทัดที่ Meta, Netflix และ Cursor และช่วยสร้างกับดูแล React Compiler ในทีมแกน React นี่คือข้อเท็จจริงเรื่องงานที่บทความนี้จะใช้ มันจะไม่เติมข้ออื่น

## pstack คืออะไร

pstack คือชุดสกิลของเธอสำหรับทำงานวิศวกรรมอย่างเข้มงวดกับเอเจนต์เขียนโค้ด เผยแพร่เป็นปลั๊กอิน บน Cursor ติดตั้งด้วย `/add-plugin pstack` README พูดตรง ๆ เรื่องเป้าหมาย: ไม่ใช่โค้ดมากขึ้น แต่เป็นโค้ดน้อยลงและคุณภาพสูงขึ้น เธอเรียกผลลัพธ์ว่าความขนานที่ไม่ต้องกลัว คุณได้สิทธิ์รันเอเจนต์หลายตัวก็ต่อเมื่อเอเจนต์ตัวหนึ่งถูกไว้ใจให้ตรวจงานของตัวเองได้

ประตูที่ใช้ทุกวันคือ `/poteto-mode` มันจับงานเข้ากับหนึ่งในยี่สิบสาม playbook (บั๊ก ร่องรอยประสิทธิภาพ ฟีเจอร์ ต้นแบบ งานข้ามคืน และอื่น ๆ) แล้วดึงสกิลอื่นตามที่ขั้นตอนต้องการ ปักมันเป็นโหมดกำหนดเองได้ด้วย Option+Enter บน Mac หรือ Alt+Enter บน Windows เพื่อให้เทิร์นถัดไปยังเห็นมัน `/setup-pstack` เลือกโมเดลของแต่ละบทบาท สกิลไม่ได้ผูกกับโมเดลเดียว

มีคู่มือสองชิ้นที่ควรอ่านคู่กับบทสรุปนี้ ภาค 1 คือ [The Complete Guide to pstack](https://x.com/poteto/status/2094457600259842065) ภาค 2 เรื่องการกำกับคนที่ฉลาดกว่าคุณอยู่ [ที่นี่](https://x.com/poteto/status/2097732320606507506) ปลั๊กอินยังมีคู่มือในรีโพ รวมถึง [Verify the result and open a PR](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/06-verify-and-ship.md)

## การตรวจงานในฐานะโครงสร้างพื้นฐาน

ความคิดที่เธอวางไว้ต้น ๆ พูดง่ายแต่รักษายาก: เอเจนต์ควรบอกได้ว่างานเสร็จหรือยัง ถ้ารันฟีเจอร์ อ่านค่า และดูหลักฐานได้ มันจะไปต่อจนงานเสร็จจริง ถ้าทำไม่ได้ คุณยังเป็นคอขวด และเอเจนต์ที่มากขึ้นหมายถึงดิฟฟ์ที่ยังไม่ถูกตรวจมากขึ้น

เธอมองความสามารถนั้นเป็นโครงสร้างพื้นฐาน ใกล้กับถนนที่ราดยางมากกว่าพรอมต์ที่ฉลาด สกิลตรวจงานที่ดีถูกคอมมิต ถูกแชร์ และถูกบำรุง คนที่ไม่ใช่วิศวกรใช้เส้นทางเดียวกันได้ หลักในปลั๊กอินชื่อ prove-it-works: "คอมไพล์ผ่าน" ไม่ใช่หลักฐาน

`/create-verification-skill` คือวิธีที่โปรเจกต์สร้างถนนนั้น มันสัมภาษณ์รีโพซิทอรี ไม่ใช่แบบสอบถาม มันหาว่าคนแตะอะไร แอปเริ่มอย่างไร อะไรขับมันได้ และอะไรนับเป็นหลักฐาน มันเขียนสกิลในโปรเจกต์ที่มีหัวข้อ Launch, Doctor, Drive, Evidence และ Cleanup พร้อม feature map ก่อนส่งมอบ มันต้องพิสูจน์สกิลหนึ่งรอบ: เปิดแอป ตรวจสุขภาพ ขับหนึ่งฟีเจอร์ เก็บหลักฐาน เก็บกวาด แล้วยืนยันว่าหลักฐานยังอยู่ ถ้าพิสูจน์ไม่ผ่าน อย่าใช้ผลลัพธ์นั้น

## Feature Map

เมื่อแอปโต "คลิกไปเรื่อย ๆ จนใช้ได้" ไม่พอดีหน้าต่างบริบทอีกต่อไป Feature Map คือคำตอบของเธอ: แผนที่ฟีเจอร์เล็ก ๆ ที่ค้นได้ เขียนจากมุมผู้ใช้ ตัวอย่างในปลั๊กอินบอกว่าไฟล์ฟีเจอร์มีสี่ส่วนตามลำดับ: ฟีเจอร์ย่อย วิธีที่คนไปถึง วิธีขับด้วยคำสั่งควบคุม และกับดัก

เธอบรรยายแผนที่ว่าเป็นความจำที่ทำให้เป็นรูปธรรม โค้ดเบสคือความจำของการตัดสินใจของทีมอยู่แล้ว แผนที่คือภาพย่อของความจำนั้น ถูกพอที่เอเจนต์จะอ่านก่อนแตะผลิตภัณฑ์ `/maintain-verification-skill` คืองานบำรุง คู่มือแนะนำให้รันอย่างน้อยทุกวัน เพราะแผนที่ที่ตามผลิตภัณฑ์ไม่ทันจะส่งเอเจนต์ไปทางที่ไม่มีอยู่แล้ว

## คันโยก

มาร์กดาวน์ที่บอกว่า "แล้วคลิกปุ่ม" ยังปล่อยให้ทุกเอเจนต์คิดสคริปต์เอง หลักที่เธอชื่อ Build the Lever เลือก CLI ควบคุมเล็ก ๆ ที่สกิลเรียกแทน คุณสมบัติที่เธอระบุใช้ได้จริง: คำสั่งไม่กี่คำที่ทำงานจริง `--dry-run` ในสิ่งที่ทำลายข้อมูล คำสั่งย่อยที่ค่อย ๆ เปิดฟีเจอร์ ข้อผิดพลาดที่บอกว่าควรทำอะไรต่อ และผลลัพธ์ที่เครื่องอ่านได้เช่น JSON เอเจนต์ใช้โทเคนน้อยลง และผู้ตรวจรันคำสั่งเดิมซ้ำได้

ในภาค 1 เธอยังเถียงกับการใช้ git worktree บนเครื่องเป็นวิธีหลักในการรันเอเจนต์จำนวนมาก worktree กินดิสก์และชนเพดานที่เครื่องใต้โต๊ะ คำแนะนำของเธอคือ cloud agent ของ Cursor: คอมพิวเตอร์จริง การตั้งค่าที่สแนปช็อตได้ และที่ว่างให้ขนานเมื่องานพัฒนาเองทำซ้ำได้ นั่นคือข้อโต้แย้งของเธอจากบทความ ไม่ใช่ข้ออ้างเรื่องรถ

## อุปมาที่วางบนพื้น

รถไม่ลอยเพราะวิศวกรที่มีชื่ออยู่ในห้อง โค้ดเบสไม่น่าเชื่อถือขึ้นเพราะเอเจนต์พิมพ์เร็วขึ้น ข้ออ้างที่น่าสนใจ และข้อเดียวที่บทความนี้จะทำ มีขอบเขตแคบกว่านั้น ถ้าทีมสร้างการตรวจงานไว้ในเส้นทางประจำวัน — feature map, คำสั่งควบคุม, สกิลที่พิสูจน์ตัวเองแล้วหนึ่งรอบ — งานเปลี่ยนผลิตภัณฑ์ที่ยากจะดูเหมือนการบินด้วยเครื่องวัดมากขึ้น และเหมือนการหวังน้อยลง

งานสาธารณะของ Lauren Tan อยู่ที่ xAI, React Compiler และตาม README ของ pstack ผ่าน Meta, Netflix และ Cursor เธอไม่ได้ทำงานที่ Tesla Tesla ในชื่อเรื่องยังอยู่บนถนน แรงยก ถ้ามี อยู่ที่เครื่องวัด

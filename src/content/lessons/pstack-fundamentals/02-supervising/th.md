บทเรียนนี้เป็นบทสรุปชุมชนโดย SuperChoice AI ไม่ได้เกี่ยวข้องหรือได้รับการรับรองจาก Cursor, xAI หรือ Lauren Tan เรียงความต้นฉบับเป็นของเธอ: [ภาค 2](https://x.com/poteto/status/2097732320606507506) ตอนเขียนคอร์สนี้ หน้านั้นตอบ HTTP 403 ดังนั้นสิ่งที่ตามมาเป็นร้อยแก้วต้นฉบับจากเอกสาร pstack และจากสำเนาสาธารณะของเรียงความ มันไม่ใช่ถอดความ

ภาค 1 เถียงว่าไม่มีอะไรสำคัญถ้าเอเจนต์ตรวจงานตัวเองไม่ได้ ภาค 2 ถามคำถามถัดไป: เมื่อมันทำได้แล้ว คุณตัดสินว่ามันควรสร้างอะไรอย่างไร ชื่อที่เธอให้ปัญหานั้นคือศิลปะของการกำกับคนที่ฉลาดกว่าคุณ บนโค้ดเบสที่ไม่มีคนคนเดียวอุ้มไว้ในหัวได้อีกแล้ว

## สองทางที่โมเดลเก่งแล้วยังพลาด

เธอระบุความล้มเหลวสองแบบที่เธอเจอบ่อย โมเดลไม่เข้าใจเจตนา เพราะคำสั่งบางหรือใส่มาไม่ดี หรือมันมีบริบทไม่พอให้ทำงานได้ถูกต้อง ทั้งสองเกี่ยวกัน การทำงานกับเอเจนต์ให้ดีคืองานใส่บริบทคุณภาพสูงเข้าหน้าต่างเป็นส่วนใหญ่ คุณได้โค้ดที่รันโดยไม่มีงานนั้นก็ได้ เธอพบว่าผลดีขึ้นเมื่อบริบทช่วยทำงานส่วนหนึ่ง

## พูดกลับ

โมเดลรุ่นเก่าชวนให้จุกจิก รุ่นปัจจุบันเขียนโค้ดได้ดีกว่าคนสั่ง ซึ่งสร้างปัญหาคนละแบบ: คุณต้องบอกผลลัพธ์ที่ต้องการโดยไม่ระบายทางเดียวที่คุณบังเอิญเห็น

เทคนิคหนึ่งที่เธอใช้คือพรอมต์อ้อม แทนการบอกบั๊ก เธอให้เอเจนต์อ่านเธรดแล้วเล่าปัญหาข้างใต้ด้วยคำธรรมดาก่อนแก้ใด ๆ พรอมต์รูปนั้นใต้ `/poteto-mode` ทำสามอย่าง มันบังคับบทสนทนาที่รกให้เป็นประโยคปัญหา มันให้คุณจับการยึดประเด็นข้างเคียงก่อนมีโค้ด และมันเลี่ยงการนำเอเจนต์ด้วยสมมติฐานของคุณ ซึ่งอาจผิดหรืออาจเล็กกว่าทางแก้ที่มันจะเจอ

การขอให้มีคนอธิบายงานกลับมาเป็นวิธีรักษาแบบจำลองระบบของคุณให้ทันด้วย นั่นคืองานของ `/teach` ใต้ฝากระโปรง เรียงความบอกว่า `/teach` เรียก `/how` และ `/why`

`/how` ตามว่าระบบย่อยรันจริงอย่างไร ถ้าพื้นที่ครอบหลายไดเรกทอรีหรือบริการ มันกระจายไปโมเดลที่เร็วกว่า `/why` หาแรงจูงใจ โค้ดบอกว่าเกิดอะไร มันไม่ค่อยบอกว่าทำไมคนเขียนแบบนั้น `/why` ค้นประวัติขนานกัน: git กับความเห็นรีวิว ทิกเก็ต เอกสารออกแบบ แชท มอนิเตอร์ ตัวตามข้อผิดพลาด และการวิเคราะห์ เท่าที่สภาพแวดล้อมไปถึง งานค้นช่วยคุณ และช่วยเอเจนต์ ซึ่งไม่งั้นจะกล่าวกลไกที่มันยังไม่ได้อ่าน

`/recall` คือชิ้นสำหรับงานที่ข้ามแชท ทรานสคริปต์เก่าคือบริบทที่คุณจ่ายไปแล้ว เอเจนต์ใหม่รับบทสรุปแน่นของงานเวอร์ชวลไลเซชันเมื่อวาน แล้วตามด้วยรายงานบั๊กใหม่ แทนการเริ่มจากศูนย์

## ทำงานย้อนจากผู้อ่าน

เธอสงสัยโหมดแผนที่ระบุการอิมพลีเมนต์และข้ามอย่างอื่น README ล้อว่าเธอไม่เชื่อในการวางแผน ข้อแก้ในเรียงความคือเธอวางแผน ผ่านโค้ด

สำหรับไลบรารีที่ใช้ร่วม เธอชอบ README-driven development: เขียนบทเรียนที่ผู้เรียกจะเดินตาม แล้วสร้างย้อนกลับไปหาเอกสารนั้น เมื่อเธอลองกับเฟรมเวิร์กไคลเอนต์ภายใน README รอบแรกเจ็บเพราะปนบทเรียน คู่มือ เรียงความสถาปัตยกรรม และเอกสาร API ในสำนวนที่เกร็ง `/technical-writing` คือมีดที่เธอลับก่อน มันใช้ Diátaxis เพื่อแยกสี่โหมด

- บทเรียน: ผู้เริ่มสร้างสิ่งที่มองเห็น
- คู่มือ: คนที่มีประสบการณ์แก้หนึ่งงานจริง
- เอกสารอ้างอิง: คำบรรยายแห้งและครบของเครื่องจักร
- คำอธิบาย: ข้อแลกเปลี่ยนและภูมิหลัง

`/unslop` เป็นส่วนของรอบนั้นเพื่อให้เอกสารยังอ่านได้ แผนที่เขียนแบบนี้ยังเป็นเป้าหมายที่เอเจนต์ตรวจตัวเองได้

## อย่ารับแบบแรก

ความผิดพลาดตอนวางแผนสองอย่างโผล่ตลอด การรับแบบแรกที่เอเจนต์ส่งกลับ และการเคี่ยวแผนนามธรรมที่ไม่มีหลักฐานข้างใต้ เมื่อมนุษย์เขียนเอกสารออกแบบ หลายรอบเป็นเรื่องปกติ เอเจนต์ทำให้ข้ามรอบได้ง่าย และทำให้แทนที่รอบเหล่านั้นด้วยเอกสารที่ยาวขึ้นซึ่งยังไม่แตะระบบได้ง่ายเช่นกัน

playbook ใน pstack ไม่ใช่สกิลแยก มันเป็นไฟล์อ้างอิงข้างใน `/poteto-mode` โหลดเมื่องานตรง ส่วนหนึ่งเพื่อไม่ให้เวิร์กโฟลว์ที่ไม่ได้ใช้กินโทเคน README ระบุยี่สิบสามเล่ม คุณมักไม่ต้องเรียกชื่อ คุณพูด `/poteto-mode` แล้วอธิบายงาน

playbook ทำต้นแบบคือรูปแบบการวางแผนที่เธอชอบ ขอสองสามทางเลือก แล้วให้ verification skill ขับมันและนำภาพหน้าจอหรือเวลากลับมา สำหรับการเปลี่ยนด้านภาพ แบบต่าง ๆ อยู่หลังสวิตช์ในแอปหรือในไดเรกทอรีทดลอง ประเด็นคือเชิงประจักษ์: เอเจนต์ตอบคำถามเปิดของตัวเองด้วยการรันบางอย่าง และมีที่ให้ทำให้คุณประหลาดใจ

`/architect` คือลูปที่หนักกว่า สำหรับขอบเขตที่โค้ดอื่นจะพึ่ง เฟสในเรียงความ:

- ปักปัญหาด้วย `/how` และ `/why`
- ร่าง: ตัววิ่งอิสระ มักข้ามตระกูลโมเดล แต่ละตัวร่างจุดเรียก ชนิดข้อมูลแกน ลายเซ็นสาธารณะ และเหตุผลสั้น แล้วกรองแบบเรื่องส่วนต่อที่ตื้นและความล้มเหลวของการออกแบบที่รู้จัก
- ให้โมเดลคนละตัวกับคนร่างเป็นผู้ตัดสินข้าม
- ลงมือตามแบบ และยกขึ้นถ้าฟังก์ชันต้องการสถานะที่แบบไม่มี
- ทิ้งแบบเมื่อหลักฐานบอกว่าผิด

สัญญาณเชิงประจักษ์ที่เธอระบุ: ทางลัดเดียวกันโผล่ที่จุดเรียกที่ไม่เกี่ยวกัน หรือชนิดข้อมูลต้องใช้ทางหนีอย่าง `any` หรือการแคสต์บังคับ นั่นคือสัญญาณให้เริ่มใหม่ ไม่ใช่สัญญาณให้เพิ่มทางหนีอีกช่อง

เธอไม่สนใจรีวิวแผนนามธรรมแบบหาเรื่อง เอเจนต์คิดความเสี่ยงเชิงทฤษฎีให้เอกสารชนิดนั้น ให้คำถามเปิดได้คำตอบจากต้นแบบและการตรวจงาน

## แผน หลังจากแบบเป็นจริง

เมื่อเธอต้องการแผนที่เขียน มันมาหลังแบบที่เธอเชื่อ ผ่าน playbook วางแผนหลายเฟส: `/poteto-mode` พร้อมคำขอให้เปลี่ยนแบบเป็นแผน ทุกรายการสร้างรอบหลักฐาน playbook บอกเอเจนต์ว่าเทสต์อย่างเดียวไม่ใช่การตรวจ โค้ดต้องถูกรัน สคริปต์ตรวจโครงสร้างของแผน แต่ละพูลรีเควสต์เล็ก สำหรับงานใหญ่มากเธออาจคอมมิตแผนชั่วคราวเพื่อให้เอเจนต์อื่นเห็น แล้วลบเมื่องานจบ เธอไม่เก็บแผนไว้เป็นเอกสารถาวร

วันส่วนใหญ่ส่วนติดต่อสั้นกว่าทั้งหมดข้างบน เธรดที่มีบริบทแล้วได้ `/poteto-mode do it` หรือคำขอให้ทำซ้ำด้วย verification skill และโชว์วิดีโอถ้ามันเกิดซ้ำบนสาขาหลัก สกิลอื่นทำงานเพราะโหมดส่งต่อไป

## สิ่งที่ข้อสอบจะถือว่าคุณพูดได้

คุณควรบอกชื่อความล้มเหลวสองแบบได้ อธิบายได้ว่าทำไมการเล่ากลับมาก่อนแพตช์ บอกได้ว่า `/teach`, `/how`, `/why` และ `/recall` มีไว้ทำอะไร บอกสี่โหมดของ Diátaxis และอธิบายการทำต้นแบบกับ `/architect` ว่าเป็นการวางแผนที่ทำในโค้ด คุณควรพูดได้ด้วยว่าการ babysit พูลรีเควสต์หยุดที่สถานะพร้อมรวม และการ shipping คือการตัดสินใจแยกเพื่อลงสแตกที่เอเจนต์ใหม่ตรวจแล้ว
